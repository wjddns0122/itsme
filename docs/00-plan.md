## 1. 이번 단계의 목표

**3일 안에 실제 물건 30~50개로 돌아가는 MVP를 만들고, 측정한 수치로 PSST 발표를 완성한다.**

데모가 끝났을 때 아래 다섯 가지를 보여줄 수 있어야 한다.

1. 관리자가 사진 한 장으로 습득물을 등록한다 (AI가 양식을 채운다).
2. 분실자가 시설을 검색해서(QR 없이, 집에서도) 로그인 없이 자연어로 신고한다.
3. 시스템이 비슷한 습득물 후보를 찾아 보여준다.
4. 분실자가 "내 물건 같아요"를 누르면 정답을 드러내지 않는 확인 질문에 답하고, AI가 답변을 비공개 특징과 비교해 관리자에게 보여준다. 관리자가 승인하거나 추가 증빙을 요청한 뒤 반환 처리한다.
5. 실측 수치: 등록 시간, 신고 시간, Top-3 재현율, 오매칭률, 가짜 확인 요청을 걸러낸 비율 (표본 수 포함).

PSST 주 담당: Problem → A (설문·인터뷰 시각화) / Solution → 본인 + B (MVP, UI/UX) / Scale-up → C (경쟁사, 특허, 시장, 수익모델) / Team → 본인.

결정 권한: 범위와 우선순위는 본인이 정한다. 화면 구성은 B가 제안하고 본인이 승인한다. 브랜드는 A가 정한다. 특허·법률은 C가 조사하고 결론은 함께 정한다.

특허 검토 후보 (C가 선행기술을 조사한 뒤 판단한다. 아직 신규성·진보성이 확인된 발명이 아니다)
1. 습득물 사진과 분실 신고 자연어를 같은 형식으로 바꿔 비교하는 매칭 방법
2. 물품 특징·시간·장소를 함께 쓰는 후보 추천 방법
3. 같은 사람의 중복 문의를 찾아 묶어 관리하는 방법
4. 비공개 물품 특징 기반 소유권 확인 보조: 공개·비공개 정보 분리, 정답을 드러내지 않는 확인 질문, 답변 의미 비교, 물품별 단계적 추가 증빙, 허위 요청 제한 (C의 1순위 조사 대상)
5. 여러 시설의 분실물 데이터를 연결한 통합 탐색 방법
6. 기억이 불완전한 신고를 위한 동적 가중치와, 일치도·정보 충족도를 분리한 후보 추천
7. 분실자가 올린 여행 사진에서 물품 특징을 뽑아 습득물과 비교하는 방법
8. 상황 기반 질문으로 분실 정보를 보완하는 방법 (P1)

## 4. 디자인 ↔ 개발 협업 규칙

1. **개발은 디자인을 기다리지 않는다.** Day 1~2 오전까지는 shadcn/ui 기본 스타일로 만든다. 디자인이 오면 토큰(색·폰트·둥글기)부터 적용한다.
2. Figma 프레임 이름 = 화면 ID (`A-03 습득물 등록`). `03-screens.md`의 ID와 같아야 한다.
3. B는 화면마다 **빈 상태·로딩·에러** 세 가지를 함께 그린다.
4. 전달 단위는 "화면 하나 완성"이다. 전체가 끝날 때까지 모았다가 한꺼번에 주지 않는다.
5. 문구는 `03-screens.md`에 적힌 문구가 기준이다. 바꾸고 싶으면 문서를 고친다.

## 5. 컷 라인 (시간이 부족할 때 버리는 순서)

범위가 P0 40개로 늘었다 (인터뷰, 소유권 확인, 기억 부족 대응 반영). 1인 3일로 전부는 어렵다. 데모는 세 기둥, **빠른 등록 · 자동 탐색 · 안전한 반환**만 확실히 보여준다.

위에서부터 먼저 버린다. P0 핵심 흐름(등록 → 신고 → 후보 → 소유권 확인 → 반환)과 같은 연락처 신고 묶기(FL-025)는 끝까지 지킨다.

1. 대시보드 주간 차트 (FL-061) → KPI 숫자만
2. 내 사진으로 찾기 (FL-027) → 디자인 시안으로만 보여준다
3. 관리자 자연어 검색 (FL-015) → 필터만
4. 관리자 대리 신고 (FL-024) → 데모 시나리오에서 제외
5. 소유권 확인 요청의 사진 첨부 → 텍스트 답변만
6. 빠른 등록 모드 (FL-016) → 일반 등록의 [저장하고 계속 등록]으로 대신
7. AI 답변 비교 (FL-044) → 관리자가 직접 비교한다. 분류별 확인 질문은 유지
8. 문의 기록 (FL-026) → 같은 연락처 묶기만 남긴다

새 습득물 자동 알림(FL-050)과 시설 찾기(FL-028)는 버리지 않는다. "한 번만 신고하면 이후에는 시스템이 찾아준다"는 핵심 원칙을 보여주는 기능이다 (ADR-026). QR(FL-071)은 P1로 내렸다.

## 8. AI로 개발하는 방법

1. Claude Code 세션을 시작하면 `CLAUDE.md`가 자동으로 읽힌다.
2. 티켓 하나씩 맡긴다: `/ticket FL-011`. 명령이 티켓의 참고 문서를 읽고, 계획을 말하고, 구현 후 `pnpm check`와 수용 기준 체크까지 한다.
3. 결과를 수용 기준으로 직접 확인한다. 커밋 전에 `/review-diff`로 코드 리뷰·보안 점검을 받는다.
4. 결과가 괜찮으면 커밋한다 (`FL-011: ...`).
5. AI가 문서에 없는 규칙을 만들려고 하면 멈추고 `07-decisions.md`에 질문으로 남긴다.
6. 여러 티켓이 끝나면 `/sync-docs`로 코드와 문서가 어긋난 곳을 맞춘다.

Claude Code 설정 전체 구조는 `CLAUDE.md` §9.
