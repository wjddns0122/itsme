### ADR-001 · 한 앱
- 이유: 1인 개발. 인증·배포·타입을 공유하고 별도 API 서버를 없앤다.
- 대가: 분실자 화면과 관리자 화면의 배포가 묶인다. MVP에서는 문제없다.

### ADR-003 · 학습 없는 매칭
- 이유: 3일 안에 학습 데이터를 모을 수 없다. 사진을 텍스트로 바꾸면 분실자의 문장과 같은 공간에서 비교할 수 있다.
- 대가: 사진끼리의 미세한 시각 비교는 못 한다. 대신 관리자가 소유권 확인 단계에서 사진을 직접 본다.

### ADR-004 · 서버 경유
- 이유: 비로그인 사용자에게 테이블 접근을 열면 RLS 실수 하나로 다른 사람의 신고·연락처가 샌다.
- 대가: 분실자 기능은 모두 Server Action으로 만들어야 한다.

### ADR-006 · 사진 비공개
- 이유: 사진을 보여주면 누구나 사진을 보고 특징을 말해 가로챌 수 있다. 비공개 특징이 소유권 확인의 근거다.
- 대가: 분실자가 "이게 내 건지" 눈으로 확인할 수 없다. 공개 설명을 충분히 구체적으로 써야 한다.
- 재검토: 흐리게 처리한 썸네일 공개를 Phase 1에서 실험.

### ADR-008 · 임베딩 모델 (임시)
- Claude API에는 임베딩 전용 모델이 없어 별도 서비스를 쓴다.
- 후보: OpenAI `text-embedding-3-small`(저렴, 한국어 무난), Voyage AI 다국어 모델, Supabase 내장 모델(한국어 약함).
- 확인 방법: Day 1 스파이크에서 한국어 설명 10쌍(같은 물건/다른 물건)의 코사인 유사도 분포를 본다. 같은 물건 쌍과 다른 물건 쌍이 잘 갈리면 확정.
- 바꾸면: 마이그레이션(차원 변경) + 전체 재임베딩 + `COS_LOW/HIGH` 재보정.

### ADR-009 · Claude 모델 (임시)
- 기본은 `claude-opus-5-5` (정확도 우선). thinking을 끌 수 없으므로 `effort: "low"`로 지연을 줄인다.
- 사진 분석 p95가 8초를 넘으면, 더 빠르고 싼 모델(예: `claude-haiku-5-5`)을 같은 평가셋으로 돌려 **분류 정확도·지연·건당 비용**을 비교하고 팀장이 결정한다.
- 모델명은 환경변수라 코드 변경 없이 바꿀 수 있다.

### ADR-011 · 이메일만 (임시)
- 이유: Resend로 바로 붙일 수 있고 비용이 없다. 문자·알림톡은 발신번호 등록, 템플릿 심사가 필요하다.
- 우려: 한국 사용자는 이메일보다 문자·카카오를 더 본다. 설문으로 확인한다 (Q1).

### ADR-013 · AGENTS.md
- 배경: Next.js 16의 `create-next-app`이 `AGENTS.md`를 만들고, `next dev`가 실행될 때마다 그 안의 Next.js 안내 블록을 다시 써넣는다.
- 결정: 처음 계획한 "`AGENTS.md` → `CLAUDE.md` 심볼릭 링크"는 버린다 (링크면 `next dev`가 `CLAUDE.md`를 덮어쓴다). `CLAUDE.md` 첫 줄에 `@AGENTS.md`를 두어 불러온다.

### ADR-014 · Claude Code 설정 공유
- 참고한 구조: CLAUDE.md, CLAUDE.local.md, .mcp.json, .claude/{settings, rules, commands, skills, agents, hooks}.
- 결정: 팀 공통 설정은 git에 올리고, 개인 설정(`CLAUDE.local.md`, `.claude/settings.local.json`)은 `.gitignore`로 뺀다.
- 훅이 막는 것: 루트·홈 삭제, `.env` 읽기·수정, DB reset·DROP, force push, `vercel --prod`, lockfile 직접 수정, 커밋된 마이그레이션 수정.
- 사람 확인이 필요한 것(`ask`): `pnpm add/remove`, `supabase db push`, `git push`, `vercel`.
- 대가: 훅은 node로 JSON을 읽는다 (jq 불필요). 셸 명령 패턴 검사라 완벽하지 않다. 권한 설정과 사람 확인이 1차 방어선이다.

### ADR-016 · 문제 재정의와 타깃
- 근거: 2026-11-25 현장 인터뷰 (`01-prd.md` §1-2). 스키장은 하루 수십~100건, 문의가 습득물보다 많고, 반복 문의 때문에 본업에 집중하기 어렵다고 답했다.
- 결정: 핵심 메시지를 "분실물은 찾아주고, 관리 업무는 줄여주는 AI SaaS"로 바꾼다. 대학교는 접근이 쉬워 MVP 테스트 장소로, 스키장은 업무 부담이 뚜렷해 첫 사업화 대상으로 둔다.
- 주의: 인터뷰 4곳을 관광산업 전체로 일반화하지 않는다. 도입 의향과 절감 시간은 추가로 검증한다 (Q11).

### ADR-017 · 반복 문의 묶기
- 방법: 연락처를 정규화한 `contact_key`로 같은 시설의 신고와 문의 기록을 묶는다. 설명 기반 중복 감지는 P1.
- 분실자에게 숨기는 이유: 남의 전화번호를 입력해 그 사람의 신고가 있는지 알 수 있으면 개인정보가 샌다.
- 대가: 연락처를 다르게 적으면 묶이지 않는다. 관리자의 연락처 검색과 P1 설명 기반 감지로 보완한다.

### ADR-019 · 매칭과 소유권 확인 분리
- 배경: 발표·피드백에서 가장 많이 받은 질문은 "진짜 그 사람 물건인지 어떻게 아나, 아무나 자기 거라고 하면?"이었다. AI는 물건이 비슷한지는 찾지만 그 사람이 주인인지는 판단할 수 없다.
- 결정: 매칭과 확인을 나눈다. 확인은 (1) 분류별 고정 질문에 주관식 답변, (2) AI가 답변과 비공개 특징을 항목별로 비교해 관리자에게만 보여주기, (3) 관리자의 승인 / 추가 증빙 요청 / 보류 / 거절, (4) 고가품·지갑·신분증은 수령 때 잠금 해제·일련번호·신분증 확인, (5) 시도 제한으로 한다.
- 버린 대안: 물건마다 AI가 비공개 특징을 보고 질문을 새로 만드는 방식. 질문이 특징의 존재를 드러내기 쉽다 ("각인이 있나요?"). 팀원 C가 특허 관점에서 검토할 때는 "질문이 정보를 흘리지 않는다"는 조건을 함께 본다.
- 한계: 특징이 없는 흔한 물건은 이 방법으로도 확실히 판단할 수 없다. 관리자가 보류하거나 직접 확인한다. 연락처 인증은 연락처가 진짜라는 것만 확인할 뿐 소유를 증명하지 않는다 (P1).

### ADR-020 · 검색은 관대하게, 반환은 엄격하게
- 배경: 자기 물건이어도 브랜드, 색, 흠집 위치까지 기억하는 사람은 드물다 (특히 스키장 장갑·고글). 모르는 항목을 0점으로 두면 진짜 주인도 못 찾는다.
- 결정: 분실 신고의 모든 항목에 "잘 모르겠어요"를 두고, 모르는 신호는 점수에서 뺀다. 대신 비교에 쓴 신호의 비중(정보 충족도)을 따로 내서, 낮으면 "정보가 적어요" 표시와 함께 보여주고 알림은 보내지 않는다. 반환 단계에서는 정보가 적을수록 추가 증빙을 요구한다 (`01-prd.md` F7-10).
- 대가: 정보가 적은 신고는 후보가 넓게 나와 관리자 확인이 늘 수 있다.

## 3. 인터뷰·설문에 꼭 넣을 질문 (Q1, Q8~Q10 해결용)

관리자 인터뷰 (팀원 B)
1. 습득물이 들어오면 지금 어떻게 기록하세요? (장부, 엑셀, 사진, 기록 안 함)
2. 1건 기록하는 데 얼마나 걸리세요? 하루에 몇 건 들어오나요?
3. "물건 잃어버렸는데 있나요?" 문의는 하루 몇 건이고, 1건에 얼마나 걸리세요?
4. 주인인지 어떻게 확인하세요?
5. 보관 기간이 지나면 어떻게 하세요? (경찰 제출, 폐기, 계속 보관)
6. 사진은 무엇으로 찍으실 것 같아요? (개인 폰, 시설 태블릿)
7. 이런 도구가 있으면 시설에서 돈을 낼 것 같나요? 얼마 정도? 누가 결정하나요?
